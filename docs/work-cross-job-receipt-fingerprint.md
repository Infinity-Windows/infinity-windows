# Canonical retained clock receipt fingerprint — held checkpoint 6

The K5 receipt binding hashed `to_jsonb(receipt_row)::text`. PostgreSQL formats the five `timestamptz` values in that row using the current session TimeZone. An unchanged receipt could therefore fail replay after the connection's zone changed. K6 uses one shared private `_work_cross_job_clock_receipt_fingerprint(work_activity_clock_receipts)` function for stamp, admission and replay.

The immutable definition is SHA-256 of UTF-8 PostgreSQL JSONB text of one ordered array: the literal `work_clock_receipt_fingerprint_v1`, then all 15 existing receipt columns in their declared order: client_id, profile_id, shift_id, action, outcome, tapped_at, arrived_at, clock_checked_at, clock_skew_ms, used_tap_time, review_reason, source_created_at, receipt_protocol, setup_payload_digest, recorded_at. Each of the five timestamp positions is `extract(epoch from timestamp) * 1000000::numeric`. This preserves exact microseconds as a numeric value without floating point or bigint range reduction. Finite instants do not depend on TimeZone, DateStyle, IntervalStyle, extra_float_digits or localized date formatting. JSON null remains null; UUID/text/Boolean/integer values retain their original types. PostgreSQL's permitted timestamp infinities retain distinct JSON scalar representations. No stored receipt fields or public JSON results are rewritten. The retained receipt has no stored JSON-result column; the original public readers and timestamp codec remain unchanged.

This is a new held pre-release contract, not an upgrade of already-installed K5 data. K5's hash definition must never be silently applied to installed receipts, and no migration backfills or rewrites private request records. A future receipt-schema change must explicitly version this field definition and receive source review; the fixture asserts the complete current column list.

The shared helper is private, immutable, strict, SECURITY DEFINER with a fixed search_path. Its body and metadata are in the bounded original-clock capability dependency list; an additional cheap pg_proc predicate pins the complete helper metadata and exact ACL, including strictness and cost. The full v2 catalog independently pins it. Legacy readiness and ordinary paid receipt recording do not evaluate the whole catalog. The paid break/return/out paths return before the clock-in-only request/fingerprint queries. Full-catalog drift tests replace the helper and alter its metadata/ACL while proving those paid safety actions remain available.

The existing `_work_activity_clock_setup_digest` already passes its input timestamps through `_work_activity_iso`, which formats explicit UTC with six fractional digits. Its original payload digest, all fields and version0/1 semantics are preserved. Cross-zone fixtures exercise actual original requests and retries with non-null latitude/longitude and Unicode notes, not a stand-alone hash comparison. Public `time_shifts` timestamp text retains PostgreSQL's normal session rendering; the returned row must equal the original stored row as rendered in the retry session. The retained JSON receipt reader continues to return its original UTC wire value unchanged.

The isolated PGlite fixture tests UTC→America/Denver and Denver→UTC for version1, registered version2, unchecked-clock paid fallback, and capture-disabled authority paid fallback. The authored v2 switch is still false; fixture enablement is explicit and simulation-only. It verifies no extra shift, receipt, version record, allocation, source, history, command or frame writes, and tests real receipt corruption by one microsecond in both zones while the source catalog still matches. It also checks every bound field, nulls, infinities and serialization settings. ALTER ROLE/DATABASE defaults are saved/restored in a transaction and their declared values are applied to the same PGlite session. This is not fresh-login proof. Genuine PG17 fresh sessions inheriting role/database TimeZone defaults remain a root-owned gate.

The private table shape and eight-table retention/merge registry are unchanged. Activation remains false; the migration ends with ROLLBACK. All 42 full-feature acceptance cases remain open.

A separate source-extraction audit found an existing legacy limitation: the original setup payload digest includes double-precision latitude/longitude through JSONB. Changing `extra_float_digits` from 1 to -15 changes that original digest for non-null coordinates, in both UTC and Denver. This predates K6 and is not a receipt-fingerprint issue. K6 does not weaken its comparison, reinterpret historical payloads, or change that old digest. Deployments must retain the existing float serialization setting for keyed retries until an independently reviewed compatibility solution exists. The new receipt fingerprint has no float fields and is independently stable under that setting change. See `verify-work-cross-job-serialization-audit.mjs` and the checkpoint's `LEGACY-SERIALIZATION-AUDIT.json`; this audit is source simulation, not a provider default check.
