# Foreman crew unit records

Foremen, supervisors and owners can open **Record crew work** in Current Work or a job’s Custom Data. They can select a saved unit, select a map opening (which keeps its map identity), or build a unit with the existing unit builder. They select one or more active internal crew members, the actual work date, stage, status and optional spoken/typed notes. No job clock or unit timer is required to file the record.

Statuses distinguish an assignment for future work, partially completed work, and a completed stage. Completing the Installing stage offers an explicit **Entire installation finished (all visits)** checkbox. This updates the custom unit’s completion fact, not the legacy map’s installation/QC workflow. An RO check, flashing or hardware entry never silently completes the entire unit. Map status, QC approval, measured sessions and payroll punches remain unchanged. The ordinary install sheet also now exposes its existing one-person credit picker to foremen on unassigned and self-assigned openings.

## Data and reliability

- The shared custom-work queue saves the payload under the signed-in account before sending. Queued or refused records remain visible and recoverable through the existing queue controls. This uses the existing queue and does not claim to fix all app-wide offline problems.
- `record_crew_work` validates the caller and selected people server-side. Partners, inactive callers and ordinary installers cannot file on behalf of crew. Installers can read the same job-scoped records as the existing Custom Data area.
- The unit mutation, crew record, people, history and idempotency receipt commit in one transaction. Repeated requests use the original command ID and cannot create a second report. Different payloads cannot reuse that receipt. Existing-unit revision checks reject stale edits.
- Existing map openings are reused. Duplicate new names within the job are refused with instructions to select the existing unit or distinguish a different unit by floor/building.
- Records keep the person who filed the report separate from the people credited and the work date separate from the submission timestamp.
- Retrospective attribution has no measured labor duration. Units with any untimed reported work are excluded from pricing samples, even when some other visits were timed. A future reviewed reconciliation feature would be needed to restore sample eligibility.
- Account-removal history counts include crew attribution. Records follow the existing job and unit deletion cascades. Profile removal preserves the record until the existing retention process ultimately removes the profile; participant links then cascade and the filer becomes null.
- This is a historical assignment/work ledger, not an exclusive unit reservation system. Original records remain visible; a correction never deletes or rewrites one (see below).

## The Work front door's compact action (20261049000000)

The crew redesign's Work screen (`pages/work/WorkScreen.tsx`) carries its own narrower action, **Add contributors**, below the lead row — foreman+ write, installer read-only. It reuses this same ledger (`crew_work_records`, `crew_work_record_people`) rather than a second one, but through two routes distinct from `record_crew_work` above:

- **`record_stage_contributors`** takes only a reference — an existing saved unit id, or a mapped opening id (which gets its one necessary companion unit, built from the plan's own data, the first time it is used) — never unit facts, a project reassignment, a filer or `whole_complete`. The project and unit are resolved and locked server-side. Only a partial or finished stage, never an assignment. Dedupe is semantic: it compares the requested people against every EFFECTIVE (nonvoid, partial/finished) report already on that exact unit + canonical stage + work date, so overlapping submissions only ever add who is actually new, and an exact repeat — same request id or a fresh one — adds nobody and files no report at all.
- **`correct_stage_contributors`** requires a bounded, nonblank reason and the digest `stage_contributor_summary` last handed back for that same unit/stage/date. The digest hashes the actual source evidence (report id + person), not merely the resulting distinct-person set, so voiding someone and re-adding them under a new report still changes it — a correction built from a now-stale view is refused, not guessed. It voids (`voided_at`/`voided_by`/`void_reason` on `crew_work_record_people`; the row and its original report are never deleted) the people being removed and, in the same transaction, can append one new report for the people being added — eligibility and the same finite, not-future date rule apply to additions; removing a since-retired worker does not, so a correction can also clean up old evidence. `voided_by` references `profiles` `on delete set null`, independent of `voided_at`/`void_reason`, so a corrected row outlives a deleted actor with its timestamp and reason intact.
- Both routes additionally require each named worker to share the caller's test/real partition and pass the same job-visibility rule the caller themselves must pass (`_ai_job_visible`) — `crew_work_record_people` has no direct `project_id` column, so the table-level sandbox trigger cannot trace and guard it the way `crew_work_records`/`custom_work_units`/`custom_work_history` already are; this is enforced in the RPC body instead. `record_crew_work` itself was hardened the same way in this migration, so the older full-unit route cannot be used to cross that boundary either — its intentional assignment/full-edit/whole-completion behavior is otherwise unchanged.
- `stage_contributor_summary(unit_id)` is the read both panels and `correct_stage_contributors`'s staleness check use. A report's `project_id` is set once, at filing, and a unit can later move to a different job (`custom_work_command`'s `unit`/`link` action) — so a row is only shown when BOTH the unit's current project and the report's original project independently pass the visibility rule; either side alone becoming a hidden test project, or deleted, drops the row.

## Release and verification

Apply `20261023000000_foreman_crew_unit_records.sql` before deploying this frontend, and `20261049000000_foreman_unit_contributors.sql` before the Work front door's contributor action. The second adds void columns, a lookup index, hardens direct report/history read policies using a caller-bound visibility helper, and adds `_stage_contributor_digest`/`stage_contributor_summary`/`record_stage_contributors`/`correct_stage_contributors`, and replaces `record_crew_work` with the hardened version described above. Neither imports or rewrites existing timecards. The release notes are limited to foreman, supervisor and owner audiences.

Checks include the actual new and existing custom-work migrations in disposable PostgreSQL (`scripts/verify-crew-unit-records.mjs`, `scripts/verify-foreman-unit-contributors.mjs`), caller/partner/participant rules, replay and stale-edit refusals, map identity, job-deletion visibility, explicit completion and unchanged payroll/session tables — plus, for the contributor route, source-evidence digest sensitivity (a void-then-readd under a different report is detected as stale even though the distinct people match), removed/moved linked-opening revalidation under the lock, the `voided_by` FK behavior, dual-sided (unit-now vs report-then) project visibility, and the finite/not-future date rule on corrections that add people. Auth and sandbox infrastructure in that SQL harness are fixture stubs approximating the production rules, not the production definitions; `scripts/dry-run-probes/pr-foreman-unit-contributors.sql` calls the real functions against the real schema on the sandbox job, rolled back, for `scripts/db-dry-run.sh`. PGlite is a single connection and does not demonstrate concurrency. `scripts/test-stage-contributors.sh` separately uses PostgreSQL 16 with two sessions: it observes an actual blocked advisory lock, verifies overlapping additions make one companion with no duplicate workers, rejects a stale competing correction, and compares nonzero time/session/points/opening snapshots. It uses disposable platform fixtures, while the forced-rollback probe checks the real schema sequentially. Browser fixtures cover phone/desktop layout, two-person filing without a clock, reload persistence, connection failure/retry and installer visibility. These are local fixtures, not physical iPhone or live-business-record tests.
