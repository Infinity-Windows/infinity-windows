# Voice memo reliability — September 21

Owner asks to fix voice recording and quick speech-to-text. Cover description microphones, Servicing voice evidence, and legacy install memos; preserve business-record permissions and payroll.

Live baseline: the deployed description endpoint transcribed the synthetic sentence "Installed four windows and cleaned the work area" in 5.222 seconds. Test-foreman read-only metadata audit exposes zero install/service memos, so this is not evidence of the reported crew incident. Device/entry-point details requested. No crew recording is sent to any new service.

Observed implementation gaps: transcription fetches can wait indefinitely in the browser; recorder startup has no cancellation/cleanup in legacy install capture and can race with Stop/Submit; service audio saves without automatic transcription and has no local playback until upload completes; install transcription saves no text until a second, potentially slow photo/topic AI call completes. Failure in that optional call discards the successful transcript.

Implement bounded shared recorder lifecycle, retained playback/retry, deterministic MIME filenames, visible progress and bounded transcription requests, automatic service memo transcription from the original captured clip, and preserve install transcript before optional enrichment. No model/budget changes. Test real browser recording with synthetic microphone audio, stall/permission/empty/cancel behavior, service retention/retry and endpoint permission/failure behavior. Publish only after required checks; verify live using synthetic speech and read-only application checks, not real job edits.

Validation: the full unit suite passed (5,510 checks before the final pre-canceled-request regression was added); the added recorder/request/endpoint tests pass. Dictation + Servicing browser flows pass, including a native Chromium encoder, MP4 final-chunk simulation, offline IndexedDB recovery, a dropped text write, unchanged typed text, and audio-only recovery. Synthetic spoken audio encoded by Chromium and sent to the current live endpoint transcribed correctly: WebM/Opus 2.882s and MP4/Opus 2.747s. This does not establish physical iPhone microphone/AAC behavior or reproduce the unnamed crew incident. CUA connection is unavailable. No production job/timecard/crew memo was created or modified by these probes.

Release expectations: original service audio is durably queued before speech conversion; failed conversion offers retry or audio-only retention. Description dictation retains local playback/download while its form stays open. Install transcript is saved before optional topic/photo analysis, and caller-supplied storage paths/event IDs are ignored in favor of the saved, authorized attachment. No new schema, model, or AI-budget changes.

Additional format finding: Apple-encoded AAC/M4A at 16 kHz and 48 kHz each received a 502 from the live description endpoint while a WAV control succeeded. The same AAC decodes correctly in a real Chromium OfflineAudioContext. Added client-side conversion to mono 16 kHz WAV for speech recognition only; original recordings remain unchanged for storage/playback. Description and service requests use this speech copy; install transcription accepts a bounded WAV only for the original uploader or a lead after resolving the authorized attachment. Existing install memo retries download and normalize their saved original. A 6 MiB request cap covers a full 3-minute PCM clip. Native conversion of the 2.49-second AAC test took 0.198 seconds. A subsequent live normalization probe was blocked by local connection refusals to Supabase and GitHub, not an application response.
